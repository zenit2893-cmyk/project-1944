# CoD3 native script continuation bridge

This bridge implements the specific script scheduler contract identified in the supplied XEX build. It keeps the original guest capture, stack-copy, wait flags/lists, closure wrapper and task destruction code. Native Windows fibers preserve the C++ call frames that ordinary translated `blr` cannot resume.

Verified input map: `analysis/cod3-allmodule-coroutine-sites.json` contains 15 missions and 45 complete opcode-verified capture functions: timed, integer and event waits. `Prepare.ps1` checks the XEX hashes and complete-body verification fields before generating wrappers. Original images are never edited.

The transfer points are:

1. Main `824A6150`: a scope identifies the real scheduler node and shared PPCContext. Its original body still executes.
2. Closure helper `823C0B98`, only with guest LR `824A62A8`: start a child fiber and call the original helper/virtual closure wrapper. Other invocations pass through.
3. Mission capture entries: call their original 400-byte SAVE, API68 stack-copy and API76/80/84 wait body. A transfer through the scheduler buffer `829EB1C0` unwinds within the child to the capture-entry landing before parking it. It cannot fall through into the adjacent capture body.
4. Main custom-resume `blr` at `824A6480`: the original guest code has already copied its stack and restored its asymmetric 400-byte register frame. Switch to the parked native continuation and return from its capture-entry wrapper to the real C++ caller.
5. On returning to the scheduler fiber, invoke the real main-image native longjmp to the still-live `824A6150` landing. Never native-longjmp directly between fiber stacks.
6. A resumed closure's eventual ordinary return invokes the original guest bit3 setter, the persistent completion effect at `824A62AC..824A62B8`, before the current scheduler landing. Initial ordinary returns still run the original completion tail normally.
7. Task destructor `824A5D70`: cancel/unwind a parked child on its own stack, delete it from the scheduler stack, then run the original guest destructor. The linked main `XexUnloadImage` wrapper cancels resident parked mission continuations before the original SDK unload.

The bridge does not reconstruct a continuation by casting guest LR to a new function. It does not restore a guessed complete PPCContext on resume. In particular, the original stream restores r3..31/f14..31/LR/CTR/SP, but leaves incoming CR/XER/VMX and guest FPSCR behavior as observed. Independent reference fixtures are generated by `integration/coroutine-reference`, separately from this implementation.

The bridge uses the SDK's `rex::thread::Fiber` wrapper for both child fibers and a bridge-owned root. That keeps ReXGlue's fiber ownership/TLS marker in sync on every switch. In the game hook, `XThread::main_fiber()` is passed into `ResumeScope`; this borrows the root that ReXGlue created for the guest thread and leaves its lifetime to `XThread`. If no SDK root exists, the isolated bridge may convert the current thread itself and later destroys only that root. After each switch, the bridge reapplies the saved scheduler host FP policy and the current guest rounding/flush bits. The actual generated restore stream's `lfd` operations disable flush mode; child MXCSR status or host exception bits must not leak into the scheduler root.

Run isolated tests:

```powershell
.\integration\coroutines\Run-Tests.ps1
```

The tests compile the main and Saint-Lo adapters, then exercise 32 independently produced original-opcode states through two yields/resumes each, across a DLL. They test both a bridge-owned root and a pre-existing SDK `rex::thread::Fiber` root; native locals, shared context identity, TLS marker, raw FPR/VMX/CR/XER values, guest FP mode, and scheduler host FP policy; normal and nonlocal completion; cancellation cleanup before mission unload; and rejection of an unsupported foreign-fiber longjmp. `test-results.json` records hashes and results. The synthetic guest bodies are test fixtures, not game replacements.

Integration is owned by the application task. After stopping the active game, merge `manifest-additions.toml` into the existing main entrypoint table. Keep `setjmp_address=0x82351CC0` and `longjmp_address=0x8234EEC0`. Run the existing strict per-target codegen wrapper so the custom PCH and `824A6480` mid-ASM hook are emitted. `template_dir` is interpreted relative to the codegen working directory by the current SDK; the supplied relative path assumes codegen runs from `cod3-pc`.

After the host and all 15 mission CMake targets exist:

```cmake
add_subdirectory("${CMAKE_CURRENT_SOURCE_DIR}/../integration/coroutines" coroutines)
cod3_enable_coroutines(cod3_pc "${CMAKE_CURRENT_SOURCE_DIR}/generated/default")
```

The helper links the core to the host, its `cod3_pc_recomp` object target (which builds the custom PCH), and all mission targets. It colocates `cod3_coroutines.dll` with the host. Retain the same pinned runtime/Release CRT ABI and strict floating-point options as the current native project.

Before launch, verify the generated main PCH contains `NoteSetjmp`/`InterceptLongjmp`, the generated `824A6150` contains `Cod3CoroutineResumeRestored()` immediately before its custom `blr`, all 45 capture wrappers link, the core DLL is staged, and `XThread::main_fiber()` is available at the scheduler hook. Then rerun the actual scene and record the outcome. Passing the isolated fixtures is not a completed gameplay, timing or physics validation.

The initial implementation explicitly rejects nested scheduler invocations, active-task destruction, mission unload with relevant continuations owned by another host thread, and cross-fiber longjmps to buffers other than the verified scheduler buffer. Such paths fail visibly through the scheduler instead of jumping into a foreign native stack. The linked unload adapter covers the game's currently observed main import path; newly discovered dynamic unload paths require the same lifecycle treatment. Neither frame rate nor any game clock scalar is changed here.
