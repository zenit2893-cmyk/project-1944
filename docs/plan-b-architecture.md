# Call of Duty 3 PC: план Б

Рабочий проект находится в `cod3-pc`, цель CMake — `cod3_pc`. Предыдущий `cod3` сохранён как исходная проверка анализа. Оба используют единственную проверенную копию данных в `game/cod3`.

Три инструмента выполняют разные проверяемые задачи:

| Инструмент | Задача в проекте | Граница совместимости |
|---|---|---|
| ReXGlue 0.10.0.5-dev.g0c7b01a | Основная генерация PowerPC → C++, runtime, память, потоки, ввод, аудио, загрузка модулей, GPU plugin | Его структуры состояния и API определяют ABI итогового приложения. |
| XenonRecomp + XenonAnalyse, `ddd128bcca99fe8bfbb99bea583c972351fa6ace` | Независимый анализ переходов, дополнительная генерация выбранных функций и проверка адаптера | Оригинальный `PPCContext` нельзя приводить к `PPCContext` ReXGlue; прямые обращения к памяти и `__rdtsc()` требуют отдельной адаптации. |
| XenosRecomp, `990d03b28a27b50277ee5d8d942e1c5f873869d1` | Извлечение и преобразование настоящих шейдеров игры в HLSL; проверка через DXC | Его кэш для Unleashed не является форматом кэша ReXGlue. Первый runtime использует `rexgpu-xenos` с D3D12. |

Установленные инструменты находятся в `tools`, готовый SDK — в `win-amd64`. Локальное окружение компилятора включается через `scripts/toolchain-env.ps1`. Пользовательский и системный PATH не изменяются.

## Генерация кода и модули уровней

В основном XEX обнаружены два коротких переходных блока, которые требовали явных границ: `0x822D0498` (4 байта) и `0x822D2140` (8 байт). Содержимое проверено двумя независимыми способами, исходные инструкции не менялись. Доказательства находятся в `analysis/cod3-boundary-evidence.json`.

Все 15 DLL уровней используют один гостевой адрес `0x89000000` и загружаются игрой по очереди. SDK этой версии при совместном анализе накладывает образы друг на друга. Поэтому `cod3-pc/cmake/Invoke-Codegen.ps1` анализирует каждый модуль отдельным процессом и восстанавливает полный реестр нативных DLL. При запуске последовательностью загрузки по-прежнему управляет гостевой код игры.

Генерация, компиляция, старт процесса, отображение игры, прохождение миссии и корректность 120 FPS — отдельные проверки. Успешная компиляция не засчитывается как игровой результат. Мультиплеерный XEX имеет отдельную карту функций и требует отдельной цели и передачи состояния запуска.

## 120 FPS

До сравнения игрового поведения сохраняются исходные часы и режим vblank SDK. `vsync=false` в этой версии меняет гостевую частоту vblank, а настройка видеорежима сообщает другую частоту самой игре. Эти переключатели не считаются безопасным способом отделить отрисовку от симуляции.

В игровом коде найдены `com_maxfps`, `timescale`, `fixedtime` и `pmove_msec`. Статический анализ `com_maxfps` показал целочисленный бюджет `1000 / значение`: значение 120 даёт 8 единиц времени, что само по себе не задаёт точные 120 кадров/с. Семантику изменения частоты необходимо подтвердить работающей игрой.

Проверка будущего режима должна сравнивать одинаковые сценарии и входные данные: игровое время, движение и прыжки, стрельбу, AI, сценарные события, анимации и ролики. Измеряются уникальные отрисованные кадры; повторная презентация одного кадра не считается новой отрисовкой. `scripts/timing_analyze.py` проверяет такие трассы, но его синтетические тесты не заменяют трассы игры.

Исходные проекты: [ReXGlue](https://github.com/rexglue/rexglue-sdk), [XenonRecomp](https://github.com/hedge-dev/XenonRecomp), [XenosRecomp](https://github.com/hedge-dev/XenosRecomp), [xdvdfs](https://github.com/antangelo/xdvdfs).
