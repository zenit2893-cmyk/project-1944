# Call of Duty 3: runtime compatibility evidence

Проверено для образа `default.xex` с SHA-256 `2944EEC7D1231AD6798B5F9F8ADF8855F5E489296B22EAB45B27A577CEE23692` и ReXGlue `0.10.0.5-dev.g0c7b01a`, исходный commit `0c7b01a0ac0479801757507d80533f662fa0815d`. Это аудит загрузчика и импортов; он сам по себе не подтверждает прохождение миссий, полноценную физику или 120 FPS. Официальная [wiki ReXGlue](https://github.com/rexglue/rexglue-sdk/wiki) также описывает SDK как инструментарий, требующий ручной доводки отдельных игр.

**Что уже подтверждено.** Загрузчик распознал 189 импортов основного XEX: 179 функций и 10 переменных. Все 179 функций зарегистрированы в исходниках соответствующей версии и присутствуют среди экспортов поставленного `rexruntime.dll`. Наличие символа не означает полноценную реализацию. В 15 отдельно сгенерированных DLL миссий по 28 импортированных функций; все имеют регистрации в SDK. Их имена входят в набор импортов основного XEX. В контейнерных заголовках каждой DLL 58 записей импорта: функция обычно занимает две записи; это не 58 отдельных API. Отдельная генерация функций не подтверждает значения двух переменных каждого модуля.

Артефакты для повторной проверки: `scripts/runtime-audit-imports.ps1`, `analysis/runtime-imports.json`, `analysis/runtime-imports.csv`, `analysis/runtime-<mission>-imports.json`, `docs/reports/sdk-runtime-exports.txt`. Скрипт различает явный макрос-заглушку и зарегистрированное тело, а замечания `TODO`/`STUB` помечает для ручного разбора, не превращая все такие замечания в подтвержденные ошибки.

**Существенная ошибка загрузчика воспроизведена.** `XexModule::ReadImage()` сбрасывает карту выделений всего heap `0x80000000..0x8fffffff` при загрузке каждого XEX. Основная игра и все DLL миссий находятся в этом heap. Изолированный тест через публичный API поставленного SDK загрузил основной XEX и данные Saint-Lo без выполнения игрового entry point. После загрузки миссии состояние основного выделения изменилось с 3 (reserve+commit) на 0 (free), и резервирование поверх основной игры стало разрешено. Первые 64 байта основной игры остались прежними: теряется учет памяти, а не немедленно весь ее контент.

Подготовлен `integration/rexglue-patches/0001-preserve-xex-heap-reservations.patch`. Он сохраняет чужие выделения, явно отслеживает собственную память модуля, отклоняет пересечение и освобождает собственную неудачную попытку перед повтором с devkit-ключом. Изолированная версия исправленного загрузчика прошла 13 проверок, включая принудительный неудачный retail-декод с успешной devkit-попыткой, конфликт двух образов по одному адресу и выгрузку. Полный заменяющий DLL должен дополнительно пройти тот же публичный API тест и запуск игры. Подробности, границы проверки и проверка ABI находятся в `integration/rexglue-patches/README.md`.

**Известные неполные импортированные API.**

| --- | --- | --- |
| `XamShowMarketplaceUI` | `REX_EXPORT_STUB`, только предупреждение; регистр результата не меняется | Магазин требует отдельного решения, если игра вызывает этот путь. Это не доказанный блокировщик загрузки одиночной игры. |
| `XamShowMessageBoxUIEx` | Предупреждает один раз и возвращает 0 | Показ диалога и завершение соответствующей операции не реализованы. Нужен настоящий UI/overlapped-контракт при достижении этого вызова. |
| `RtlCaptureContext`, `RtlUnwind`, `__C_specific_handler` | Зарегистрированные тела содержат только предупреждение о заглушке | Не подтверждена обработка гостевых исключений. Все три импортируются также DLL миссий. |
| `RtlRaiseException` | Обрабатывает исключение именования потока; для настоящих C++ и прочих исключений вызывает debug break | Не считать успешно разрешенный символ поддержкой SEH/unwind. Сначала установить фактический вызывающий путь, затем исправлять контракт. |

Основание: `src/kernel/xam/xam_ui.cpp:553`, `src/kernel/xboxkrnl/xboxkrnl_rtl.cpp:557`, `src/kernel/xboxkrnl/xboxkrnl_debug.cpp:129`, `src/kernel/xam/xam_user.cpp:682` в закрепленном SDK. Общий макрос предупреждающей заглушки определен в `include/rex/hook.h:58`.

**Потоки, звук и управление.** `ExCreateThread`, TLS, события, семафоры, mutex/critical-section и ожидания представлены реальными реализациями. Assertions в `KeResetEvent` и `KeInitializeSemaphore` относятся к неуспешному поиску/созданию объекта; их наличие не доказывает, что обычный вызов всегда падает. Следующие реальные проверки должны проследить создание рабочих потоков, выход из ожиданий, загрузку миссии и прекращение потоков при выходе.

Импортированные XAudio render-driver операции передают callback и буферы в `AudioSystem`; импортированный набор XMA использует существующий XMA decoder. `AudioSystem` вызывает перекомпилированный callback из отдельного worker через `FunctionDispatcher`; callback должен быть обнаружен и зарегистрирован, иначе аудио не заработает даже при доступных kernel API. SDL-путь инициализируется стандартным `ReXApp`. Прослушивание, синхронизация с видео и отсутствие underrun здесь не проверялись.

`XamInputGetCapabilities`, `XamInputGetState`, `XamInputSetState` делегируют InputSystem. В SDK есть SDL/XInput и клавиатурно-мышиная эмуляция контроллера. Последняя по умолчанию выключена (`mnk_mode=false`, `mnk_mouse=false`). Она умножает накопленные перемещения мыши на sensitivity и 200, превращает их в ограниченные значения правого стика и сбрасывает накопление при каждом запросе состояния. Это не нативный mouse-look. Для порта нужны проверка частоты опроса и отдельное решение для углового движения камеры; одна смена FPS не обеспечивает одинаковое управление.

Изменять скорость `Clock` ради 120 FPS нельзя: время используется ожиданиями, игровыми таймерами и физикой. Разделение рендера и симуляции относится к отдельной проверке game loop. В рамках этого аудита значения времени и гостевые инструкции не менялись.

**DLL миссий — адресные overlays.** Все 15 модулей используют базу `0x89000000`. В реальном запуске они должны регистрироваться и выгружаться по последовательности оригинальных `XexLoadImage`/`XexUnloadImage`. Путь registry должен совпадать с полной структурой диска: например `sp/saint_lo/saint_lo.dll`. Имя PE `saint_lo.xenonf.pe` не является ключом поиска. SDK нормализует разделители, регистр и префиксы `game:/`/`d:/`.

Нативные библиотеки имеют имена `cod3_pc_<mission>.dll`, находятся рядом с EXE и экспортируют `ReXModule_Register` и `ReXModule_GetImageInfo`. Загрузчик проверяет базу и размер XEX, регистрирует функции, затем вызывает гостевой `DllMain(DLL_PROCESS_ATTACH)` из гостевого потока. Отсутствие записи в registry не превращает XEX в исполняемый нативный код: дальнейшая диспетчеризация `DllMain` не получит нужные функции.

Полный проход стандартного codegen одновременно загружает все указанные DLL перед созданием снимков для анализа, что непригодно для этих совпадающих баз. Это проявилось ошибками анализа и `BaseHeap::Release` в первом полном проходе. Рабочий проект использует отдельный строгий `--target` для каждого модуля, после чего объединяет registry и CMake-цели. Все 15 отдельных проходов завершились без добавления искусственных функций-заглушек; нужно сохранять это поведение при повторной генерации.

**Переход в multiplayer.** `codmp_xenonf.xex` — второй полноценный executable с другой картой функций и той же базой `0x82000000`. Текущий `XamLoaderLaunchTitle` сохраняет путь в `loader_data.launch_path`, вызывает `TerminateTitle` и не возвращается. Потребителя `launch_path` в этой версии SDK нет; стандартный `ReXApp` после завершения основного потока закрывается. Поэтому штатного нативного перехода SP → MP здесь нет.

Для multiplayer нужен отдельно сгенерированный executable с собственной `PPCImageInfo`, картой функций и исследованным сетевым runtime, а затем явный переход с передачей launch data. Простая подмена загружаемого XEX внутри SP-приложения оставляет неправильную карту по тем же адресам. До реализации переход должен завершаться с понятной диагностикой на уровне приложения; возвращать фиктивный успех из невозвращающегося guest API нельзя. Изменение gameplay для обхода этой проблемы в аудите не вносилось.
