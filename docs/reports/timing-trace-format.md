# Формат будущих timing-трасс cod3-pc

`<workspace>\scripts\timing_analyze.py` — автономный анализатор Python 3.10+ без внешних зависимостей. Он **не подключён** к Call of Duty 3. Игровой logger, проверенные адреса состояния, input replay и захват экрана ещё требуется реализовать. Файлы тестов создают вымышленную 50-Hz симуляцию; это значение не относится к реальной частоте COD3.

Каждая строка UTF-8 NDJSON содержит один JSON-объект. Первой идёт `metadata`, последней — `end` с `capture_complete=true`. Между ними — `sim`, `frame`, `event`. Трасса покрывает непрерывный интервал активного сценария. Паузы, загрузки и потеря фокуса измеряются отдельными сценариями. Если сбор идёт с нескольких потоков, logger должен корректно объединить записи по `host_ns` и публиковать завершённый `sim` до ссылающихся на него кадров/событий. Нельзя просто сортировать по отображаемому номеру кадра и выдавать это за порядок игровой логики.

**Время — целые наносекунды.** `host_ns` берётся из QPC/steady clock независимо от гостевого таймера. `sim_ns` и `dt_ns` получают из подтверждённого авторитетного времени игры с точным преобразованием единиц; их нельзя синтезировать из Present, VBlank или host FPS. Если игра использует миллисекунды, сохранять реальную последовательность целых ms × 1 000 000, включая квантование. Положительные шаги симуляции нумеруются непрерывно; запись начала задаёт предшествующий tick. Этот формат не предназначен для смешивания независимых физических подсистем под одним вымышленным tick.

Версия v1 требует хотя бы одного положительного шага и одного кадра. Захват полностью остановленной симуляции, видеоплеера без игровых шагов или потока отрицательных/нулевых `dt` требует отдельной схемы/анализа; такой файл нельзя искусственно дополнять вымышленными шагами. Матрица паузы/кат-сцен в общем плане шире того, что покрывает этот анализатор.

## Обязательные поля

| kind | Поля |
| --- | --- |
| `metadata` | `schema="cod3-timing-v1"`, `capture_source="game"` или `"synthetic"`, `executable_sha256`, `sdk_commit` (40 hex), `scenario`, `input_sha256`, `checkpoint_sha256`, `rng_seed`, `run_id`, `instrumentation_id`, `guest_tick_frequency_hz`, `guest_time_scalar`, `start_host_ns`, `start_sim_ns`, `start_tick` |
| `sim` | `host_ns`, `tick`, `sim_ns`, `dt_ns`, `values` |
| `frame` | `host_ns`, `present_id`, `render_id`, `sim_tick`, `render_mode="native_scene"` или `"interpolated_scene"` |
| `event` | `host_ns`, `tick`, `sim_ns`, `category`, `name`, `values` |
| `end` | `host_ns`, `sim_ns`, `tick`, `capture_complete=true` |

Все SHA-256 — хеши реальных перечисленных объектов для игровых трасс. `instrumentation_id` фиксирует версию и набор проб; изменение измеряемых полей требует нового ID. `capture_source` и хеши — заявления logger, не криптографически подтверждённое происхождение. Анализатор сохраняет SHA-256 самой трассы для последующего аудита.

`values` — непустой словарь именованных наблюдений. Имя не содержит точек. Значения — конечные числа, строки или boolean; вложенные объекты/массивы не используются. Примеры полей: `position_x`, `position_y`, `position_z`, `velocity_x`, `health`, `ammo`, `animation_phase`, `root_motion_x`, `rng_state_digest`, `mission_state_digest`. Собирать целевые значения после завершения исходного шага. Фиксировать единицы и смысл каждой пробы в manifest захвата. Адреса указателей/счётчики отрисовки не подходят в качестве доказательства неизменности физики.

Категории событий: `movement`, `fire`, `ai`, `animation`, `script`, `cutscene`. `name` идентифицирует конкретное событие без точек. Например, `fire/shot`, `script/objective_trigger`, `animation/reload_marker`. События должны исходить из авторитетной игровой логики. Логирование `shot` при каждом рендере вспышки неверно. В лог сериализуются завершённые события текущего/завершённого tick; `sim_ns` сохраняет фактическое время события. Для одновременных событий logger фиксирует стабильный, объяснённый порядок. Отсутствующие категории перечисляются в отчёте и остаются непроверенными.

`present_id` увеличивается при фактическом запросе хостового Present. `render_id` увеличивается **только при новом построении изображения сцены**; повторный показ использует прежнее значение. ID должен приходить из renderer, а не увеличиваться вместе со счётчиком монитора. `interpolated_scene` — реальная отрисовка геометрии из интерполированных визуальных состояний. Перерисовка UI поверх прежнего framebuffer и image frame generation не считаются новыми сценами. Уникальность ID не доказывает визуальное качество — нужен сопоставленный захват/проверка renderer.

## Запуск

В текущем окружении доступен bundled Python:

```powershell
$env:PYTHONUTF8='1'
$timingPython = 'python'
& $timingPython '<workspace>\scripts\timing_analyze.py' `
  '<workspace>\analysis\timing\candidate.ndjson' `
  --baseline '<workspace>\analysis\timing\baseline.ndjson' `
  --target-fps 120 `
  --output '<workspace>\analysis\timing\comparison.json'
```

`baseline.ndjson` и `candidate.ndjson` пока не созданы: это имена будущих игровых захватов. По умолчанию сравнение времени и полей точное. `--wall-tolerance-ms` задаёт допустимое расхождение реального времени границ и **каждой** временной точки. Не назначать его произвольно ради прохождения теста: сначала измерить накладные расходы logger и разброс исходного запуска. Сценарии должны охватывать одинаковые ticks, а `scenario`, исполняемый файл, checkpoint, input, seed, SDK, частота часов и версия проб — совпадать.

`--tolerances <json>` принимает абсолютные допуски отдельных числовых полей, например `{"sim.position_x": 0.0001, "event.animation.reload_marker.phase": 0.001}`. Это только пример формата; такие допуски не одобрены для игры. Единицы и причины каждого допуска должны быть задокументированы. Ключи имеют вид `sim.<field>` или `event.<category>.<name>.<field>`. Незаписанное поле не проверяется. Время симуляции, последовательность шагов и порядок событий сравниваются точно.

Коды возврата: `0` — файл обработан, записанных расхождений нет или baseline не задан; `1` — есть наблюдаемые расхождения; `2` — некорректная/неполная трасса или политика. **Код 0 не означает выполненные 120 FPS и правильную физику.** Число новых кадров, средняя частота и интервалы находятся в отдельных полях отчёта. Сравнение может совпасть даже при 30 FPS; `mean_scene_render_rate_reaches_target` тогда будет false. Даже true означает лишь достижение среднего целевого числа заявленных новых кадров, не стабильные 120 FPS на дисплее.

Результат `SYNTHETIC_CHECK_ONLY` относится к вымышленным трассам. `OBSERVED_FIELDS_MATCH` относится только к записанным полям игровых трасс; `OBSERVED_MISMATCH` требует расследования. Все отчёты сохраняют `gameplay_120fps_verified=false`: offline comparator не может закрыть прохождение миссий, полноту проб, качество картинки и развёртку экрана.

Самопроверка анализатора:

```powershell
& $timingPython -m unittest discover `
  -s '<workspace>\tests' -p 'timing_test_*.py' -v
```

14 синтетических тестов проверяют независимость частот рендера/симуляции, повторные Present, удвоенную скорость, локальное ускорение с тем же общим временем, изменение clock contract, все шесть категорий событий, расхождение состояния и явные допуски, подмену input/сборки/checkpoint, пропущенные ticks, NaN, неполные записи и некорректную политику CLI. Они не являются игровыми тестами.
